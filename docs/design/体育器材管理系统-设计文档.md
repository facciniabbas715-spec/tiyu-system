# 体育器材管理系统 · 项目设计文档

> 文档版本：v1.0（设计基线）  
> 创建日期：2026-08-10  
> 技术栈：Vue3 + Vite + TypeScript + Element Plus / Spring Boot 3.x + MyBatis Plus + MySQL 8.0  
> 项目类型：企业后台管理系统（前后端分离）

---

## 1. 业务需求分析

### 1.1 项目背景

体育器材管理系统面向学校、企事业单位、体育场馆等组织，用于对体育器材的**采购入库、库存管理、借用归还、报废处置**进行全生命周期数字化管理，替代传统的纸质台账与 Excel 管理方式，解决以下业务痛点：

| 现状痛点 | 系统解决方式 |
| --- | --- |
| 器材台账分散、账实不符 | 统一器材档案 + 库存流水审计，每一件器材的出入都有单据可追溯 |
| 借用登记靠手写，超期无人管 | 借用单电子化审批，系统自动识别逾期并记录逾期天数 |
| 库存靠人工盘点，采购靠拍脑袋 | 实时库存 + 安全库存预警 + 统计报表辅助决策 |
| 职责不清、无权限区分 | RBAC 权限体系，管理员/仓库管理员/普通用户各司其职 |
| 违规操作无法追责 | 全量操作日志 + 登录日志，审计留痕 |

### 1.2 目标用户与角色

系统采用 **RBAC（基于角色的访问控制）** 模型，初始角色规划：

| 角色 | 角色标识 | 主要职责 |
| --- | --- | --- |
| 系统管理员 | `admin` | 用户/角色/菜单/字典等系统管理，全部数据权限 |
| 器材管理员 | `equipment_admin` | 器材档案、分类、仓库、库存、入库单管理 |
| 仓库管理员 | `warehouse_keeper` | 库存盘点、入库验收、领用发放、归还接收、报废执行 |
| 审批人员 | `approver` | 借用单、报废单、入库单的审核（可由管理员兼任） |
| 普通用户 | `common` | 提交借用申请、查看本人借用与归还记录、查询器材 |

> 说明：借用主体为系统内用户（含学生/教师等角色），外部临时人员需由管理员创建账号或后续扩展"访客借用"功能（见 §8 决策记录）。

### 1.3 核心业务流程

#### 流程一：器材入库流程

```
创建入库单(草稿) → 提交审核 → 审核通过 → 入库验收(库存增加 + 写库存流水) → 完成
                    └→ 审核驳回 → 修改后重新提交 / 作废
```

#### 流程二：器材借用流程

```
提交借用申请(选器材+数量+预计归还日) → 占用库存(锁定) → 审批通过 → 仓库发放(领用，扣减库存)
        └→ 审批驳回 → 解除锁定 / 取消申请 → 解除锁定
借用中 → 到期前自动提醒 → 归还登记(归还单) → 仓库验收(完好在库/损坏赔偿/丢失赔偿)
      → 全部归还 → 借用单完结；逾期归还 → 记录逾期天数与违约金
```

#### 流程三：器材报废流程

```
提交报废申请(选器材+数量+原因) → 审核通过 → 执行报废(扣减库存 + 写流水) → 处置登记(销毁/变卖/捐赠)
                    └→ 审核驳回
```

### 1.4 关键业务规则

1. **器材编码**：全局唯一，格式 `{分类代码}-{年份}-{6位流水}`，如 `QX-2026-000123`，由系统自动生成，禁止修改。
2. **库存约束**：借用审核通过后扣减在库数量；任何出库（借用/报废/盘亏）不得使库存为负，使用数据库行锁 + 乐观锁双重保障。
3. **借还规则**：
   - 同一器材单次借用数量不得超过当前在库数量；
   - 借用期限默认取器材的 `max_borrow_days`，未设置则取系统参数 `borrow.max.days`（默认 15 天）；
   - 逾期由定时任务每日扫描标记，归还时计算逾期天数，违约金按系统参数 `borrow.overdue.penalty`（默认 5 元/天）计算。
4. **库存预警**：在库数量 ≤ 器材安全库存阈值时，仪表盘与库存列表红色预警，可配置是否发送通知。
5. **数据审计**：所有单据（入库/借用/归还/报废）的创建人、审核人、审核意见、时间戳必须留痕；库存变动必须写入 `stock_record` 流水。
6. **逻辑删除**：除日志类与关联明细表外，业务主表统一使用 `del_flag` 逻辑删除，防止误删造成账目丢失。

### 1.5 非功能需求

| 类别 | 要求 |
| --- | --- |
| 性能 | 常规查询接口 P95 < 500ms；登录态基于 JWT + Redis，接口无状态可横向扩展 |
| 安全 | BCrypt 密码存储；登录验证码；接口级权限校验；敏感操作审计；参数校验防注入 |
| 可用性 | 前后端统一错误码与提示；重要操作二次确认；支持数据备份 |
| 可维护性 | 统一分层架构、统一响应结构、统一异常处理、接口文档自动化（Knife4j/OpenAPI3） |
| 可扩展性 | 模块化设计，预留消息通知、电子签章、多仓调拨等扩展点 |
| 兼容性 | Chrome/Edge 现代浏览器，最小分辨率 1280×720 |

## 2. 功能模块设计

### 2.1 模块总览

### 2.2 用户登录认证

| 功能点 | 设计说明 |
| --- | --- |
| 登录 | 账号 + 密码 + 图形验证码（服务端生成，Redis 校验，防暴力破解）；支持记住我（延长有效期） |
| 令牌方案 | JWT（Access Token 2h + Refresh Token 7d，或 24h 单令牌，见 §8）；Redis 维护会话与在线状态，支持踢出登录 |
| 安全约束 | BCrypt 加密存储；连续 5 次失败锁定 10 分钟；登录成功后更新 `login_ip/login_date` 并写登录日志 |
| 登出 | 前端清除本地令牌，后端删除 Redis 会话，记录登出日志 |
| 当前用户 | 提供 `/auth/info` 返回用户信息、角色、权限标识集合，前端据此动态渲染菜单与按钮 |
| 修改密码 | 校验旧密码；密码强度校验（8-20 位，含字母+数字）；强制修改周期可配置 |

### 2.3 权限管理（RBAC）

- **用户-角色-权限模型**：用户可拥有多个角色，角色可授权多个菜单/按钮权限，形成多对多关系。
- **权限粒度**：目录/菜单/按钮三级；按钮级权限通过后端接口 `@PreAuthorize` + 前端 `v-permission` 指令双重控制。
- **数据权限**：初始支持"全部数据"与"仅本人/本部门及以下"，通过 MyBatis-Plus 拦截器或条件拼接实现（见 §8 决策记录）。
- **动态菜单**：登录后根据权限标识生成路由表，前端 `permissionStore` 动态挂载，避免越权访问。

### 2.4 体育器材分类管理

- 树形结构（无限层级，`parent_id` + `ancestors` 路径字段），支持添加/修改/删除/排序。
- 删除校验：存在子分类或已挂接器材时禁止删除（逻辑删除 + 业务校验）。
- 分类编码全局唯一，作为器材编码前缀（如 `QX` 球类、`YP` 瑜伽类）。

### 2.5 体育器材信息管理

- 器材档案字段：编码、名称、分类、品牌、型号、规格、单位、采购单价、安全库存、最长借用天数、状态、主图、描述。
- 编码由系统按 `{分类代码}-{年}-{流水}` 自动生成，批量导入（Excel）时自动补码。
- 支持按名称/编码/分类/状态组合查询，列表 + 详情 + 编辑 + 停用/启用。

### 2.6 器材库存管理

- 库存维度：**器材 × 仓库**，一张器材可在多个仓库有库存。
- 库存变动全部由单据驱动（入库/借用/归还/报废/盘点），禁止直接手工改库存（可配置权限放开）。
- 库存流水 `stock_record` 记录每次变动的前后数量、变动类型、来源单据号，支持"一键追溯一件器材的完整生命周期"。
- 库存预警：在库 ≤ 安全库存时，列表红色标识 + 仪表盘预警卡片。
- 并发控制：库存更新使用 `UPDATE ... WHERE quantity >= 需求数` 行级原子操作 + 乐观锁 `version` 字段。
- 库存盘点：一期提供"盘盈/盘亏手工调整"（单据 + 流水留痕）与库存修正权限控制；独立盘点单流程（盘点任务、差异生成、多轮复核）作为二期扩展，不占一期表结构。

### 2.7 器材入库管理

- 入库单包含：仓库、供应商、入库类型（采购/退货退回/盘盈/其他）、明细（器材 + 数量 + 单价 + 金额）。
- 状态机：`草稿 → 待审核 → 已审核(通过) → 已验收(库存入账) / 驳回 / 作废`。
- 审核通过后由仓库管理员执行"入库验收"，此时才真正增加库存并写流水；未验收前单据可驳回，避免"审批即入账"的账实脱节。
- 支持入库单 Excel 模板导入明细、入库单打印。

### 2.8 器材借用管理

- 借用单：借用人、部门（冗余）、用途、预计归还日期、明细（器材 + 仓库 + 数量）。
- 状态机：`待审核 → 已通过 → 已领用(借用中) → 部分归还 / 已全部归还；待审核可驳回/取消`。
- 提交流程中即对所选器材做"锁定占用"（防止超借），驳回/取消自动解锁。
- 续借：借用中可申请续借（延长预计归还日），需审批，累计续借次数可配置。
- 逾期扫描：每日定时任务将超期未还的借用明细标记逾期，并触发提醒。

### 2.9 器材归还管理

- 归还登记：支持按借用单号带入明细，逐项填写实还数量与器材状况（完好/轻微损坏/严重损坏/丢失）。
- 归还单状态：`待确认 → 已确认 / 已驳回`；确认后回补库存并写流水、更新借用明细归还数量。
- 逾期自动计算：`overdue_days = 实际归还日 - 预计归还日`，生成违约金金额（可手工调整）。
- 损坏/丢失处理：生成赔偿记录（金额 + 说明），可对接后续财务流程（扩展项）；严重损坏器材转入"待报废"。

### 2.10 器材报废管理

- 报废单：仓库、报废类型（自然损耗/损坏报废/到期报废/其他）、明细（器材 + 数量 + 原因 + 损失金额）。
- 状态机：`待审核 → 已审核 → 已处置（库存扣减 + 流水）/ 驳回 / 作废`。
- 处置方式登记：销毁/变卖/捐赠/回收，记录处置日期与经手人。

### 2.11 操作日志与登录日志

- **操作日志**：后端 `@Log(title, businessType)` 注解 + AOP 切面自动记录：操作人、模块、业务类型、请求方法/URL/参数、返回结果、耗时、状态（成功/异常）、异常信息、IP 与归属地。
- 敏感参数（密码、令牌）自动脱敏。
- **登录日志**：登录成功/失败、账号、IP、浏览器、操作系统、失败原因，支持按时间/结果检索。
- 日志保留策略：支持按配置定期归档/清理（企业部署时由备份任务负责）。

### 2.12 数据统计分析

- **仪表盘（首页）**：今日借用/归还/入库数、库存预警数量、报废待审数量、器材总数与总库存价值。
- **统计报表（ECharts）**：
  - 库存分布：各分类器材数量占比（饼图）、各仓库库存量（柱状图）；
  - 借用趋势：近 12 个月借用/归还数量走势（折线图）；
  - 器材使用率排行：按借用次数 TOP 10（横向条形图）；
  - 部门借用统计：按部门汇总借用次数与在借数量；
  - 逾期统计：逾期单数、平均逾期天数、违约金汇总。
- 所有报表支持按时间范围筛选，列表结果支持 **Excel 导出**（EasyExcel）。

## 3. 数据库设计

### 3.1 设计规范

| 规范项 | 约定 |
| --- | --- |
| 数据库 | MySQL 8.0，InnoDB 引擎，字符集 `utf8mb4`，排序规则 `utf8mb4_general_ci` |
| 命名 | 表名/字段名一律小写下划线；表名前缀：`sys_`（系统）、`equipment`/`equipment_`（器材域）、`stock_`（库存域）、`borrow_`/`return_`/`scrap_`（业务单据） |
| 主键 | 所有业务表使用 `BIGINT` 自增主键 `id`；日志表可使用 `BIGINT` 自增 |
| 审计字段 | 业务表统一含 `create_by / create_time / update_by / update_time`；`del_flag` 逻辑删除（0 正常 / 1 已删除）；`version` 乐观锁（库存表） |
| 金额 | `DECIMAL(12,2)`；数量 `INT`；百分比/小数字段按需 `DECIMAL` |
| 时间 | 统一 `DATETIME`；业务日期用 `DATE` |
| 外键 | **不建物理外键**，仅保留逻辑关联列 + 索引（企业级 MySQL 常规做法：物理外键影响性能与分库分表，约束由应用层保证） |
| 索引 | 唯一约束用 `uk_`，普通索引用 `idx_`；查询频率低、重复度高、数据量小的列不建索引 |
| SQL 管理 | 使用 Flyway 管理版本化脚本（`V1__init.sql`、`V2__xxx.sql`），避免环境间漂移 |

### 3.2 ER 关系总览

```
┌────────────┐      ┌────────────┐      ┌────────────┐
│  sys_dept  │1───*│  sys_user  │*───*│  sys_role  │
└────────────┘      └────────────┘      └────────────┘
                                            │     │
                                            │     │ *
                                     sys_user_role   ┌────────────┐
                                     sys_role_menu  *│ sys_menu   │
                                                    └────────────┘

┌──────────────────┐    1:N    ┌─────────────┐
│ equipment_category│──────────│ equipment   │──┐
└──────────────────┘           └─────────────┘  │
                             equipment_stock ◄───┴── N:1 warehouse
                                    │
        ┌───────────────┬──────────┼──────────┬───────────────┐
        │               │          │          │               │
   stock_in_order   borrow_order  return_order  scrap_order  stock_record
        │               │          │            │
   stock_in_item   borrow_item  return_item  scrap_item

关联要点：
- sys_user ⟷ sys_role：多对多（sys_user_role）
- sys_role ⟷ sys_menu：多对多（sys_role_menu），sys_menu 自身树形（parent_id）
- equipment ⟷ warehouse：多对多库存（equipment_stock，含库存数量）
- 单据主表 ⟷ 明细表：1:N（order/item 成对出现）
- return_order → borrow_order：1:N（一张归还单可对应一张借用单，明细级关联 borrow_item）
```

### 3.9 数据库设计要点说明

1. **不建物理外键**：逻辑关联 + 索引 + 应用层事务保证，是 MySQL 高并发企业系统的常见取舍；Flyway 脚本中可提供 `FOREIGN KEY` 注释说明但默认不启用。
2. **单据号生成**：`Redis INCR` + 日期前缀，保证跨节点唯一；事务内生成，失败回滚不回收流水号（符合审计习惯）。
3. **库存一致性**：库存扣减/回补必须与单据状态变更在同一事务；更新语句携带 `quantity >= 所需数量` 条件并校验影响行数，防止超借超卖。
4. **状态机枚举**：所有状态字段使用 TINYINT 存储 + 字典表维护文案，后端枚举类统一管理，禁止魔法数字散落代码。
5. **数据归档**：`sys_oper_log`、`stock_record` 数据增长较快，预留 `create_time` 索引便于按月归档清理。

### 4.2 分层架构

```
┌─────────────────────────────────────────────────────────┐
│                      Controller 层                      │  ← 参数接收、调用 Service、返回 VO
├─────────────────────────────────────────────────────────┤
│                        Service 层                       │  ← 业务规则、事务边界、状态机流转
│                 （接口 + Impl 分离，事务注解在 Impl）      │
├─────────────────────────────────────────────────────────┤
│                  Mapper 层（MyBatis Plus）               │  ← 数据访问、复杂 SQL/报表走 XML
├─────────────────────────────────────────────────────────┤
│                    Entity / DTO / VO                    │  ← 领域模型与传输模型分离
├─────────────────────────────────────────────────────────┤
│   common / config / security / exception / aspect       │  ← 横切能力（响应、异常、鉴权、日志）
└─────────────────────────────────────────────────────────┘
```

设计原则：
- **单向依赖**：Controller → Service → Mapper，禁止跨层调用与循环依赖。
- **模型分层**：`Entity` 对应数据库表，禁止直接暴露给前端；`DTO` 是入参约束，`VO` 是出参裁剪，通过 MapStruct 转换，避免用 Map 传参。
- **事务边界**：写操作事务在 Service 方法上声明；库存扣减、单据状态更新、流水写入必须同事务。
- **接口规范**：RESTful + `/api` 前缀；资源命名复数名词；统一 `Result<T>` 响应（code / message / data / traceId）。

### 4.3 统一响应与错误码

```text
Result<T>：
  code     int      业务码（0 成功；401 未认证；403 无权限；5xx 业务错误）
  message  string   提示信息（中文，直接可展示）
  data     T        数据载荷
  traceId  string   链路追踪号（日志排查）

错误码分级：
  1xxx  通用参数错误（1001 参数校验失败）
  2xxx  认证授权（2001 账号或密码错误、2002 验证码错误、2003 登录已失效、2004 账号已锁定）
  3xxx  业务规则（3001 库存不足、3002 单据状态不允许操作、3003 存在子分类无法删除…）
  5xxx  系统异常（5000 未知异常）
```

### 4.4 认证鉴权流程

```
登录请求 → 校验验证码(Redis) → 校验用户名密码(BCrypt) → 查询用户+角色+权限
→ 生成 JWT(Access) + 写入 Redis 会话 → 返回 token + 用户信息
后续请求 → JwtAuthenticationFilter 解析 token → 校验 Redis 会话 → 填充 SecurityContext
→ @PreAuthorize("hasAuthority('equipment:borrow:add')") 方法级鉴权 → 进入业务
```

- 令牌失效/踢出：删除 Redis 会话键即可，无需等待 JWT 自然过期。
- 密码错误锁定：连续失败 5 次锁定 10 分钟（`login_fail_count` + `lock_time`）。

### 5.3 前端关键设计

1. **路由与权限**：静态路由只有 login/404；登录成功后 `permissionStore` 调用后端 `/auth/info` 获取权限与路由表，按角色动态 `addRoute` 挂载；刷新页面在守卫中重新恢复。
2. **请求封装**：`request.ts` 统一注入 `Authorization: Bearer <token>`，统一处理 `code != 0` 的错误提示、`401` 清除登录态并跳转登录页；开启请求防抖（同 key 短时间重复请求直接取消）。
3. **按钮权限**：`v-permission` 指令根据 `userStore.permissions` 控制按钮显隐，权限标识与后端 `@PreAuthorize` 保持一致，前端只是体验层、后端才是安全边界。
4. **字典**：`useDict` 组合式函数 + `dictStore` 缓存，页面中 `<DictTag dict-type="equipment_status" :value="1" />` 直接渲染标签。
5. **列表页标准模式**：查询表单 + 表格 + 分页 + 工具栏四段式；`useTable` 统一封装，保证所有列表页交互一致、代码量最小。
6. **状态机展示**：单据状态字段在后端枚举 + 字典表定义，前端只渲染字典文案与 `el-tag` 颜色（如待审核=橙色、已通过=蓝色、借用中=绿色、逾期=红色），不硬编码。
7. **全局反馈**：提交按钮 loading 防重复点击；删除/驳回/作废等敏感操作统一 `ElMessageBox.confirm` 二次确认。

## 8. 关键决策记录与待确认事项

以下为本设计基于企业项目标准所做的默认决策，请审阅确认；如有不同意见请指出，我会调整设计文档后再进入实现计划。

| # | 决策点 | 设计选择 | 理由与备选 |
| --- | --- | --- | --- |
| D1 | 认证方案 | JWT + Redis（Access Token 2h，支持踢出） | 前后端分离无状态扩展；备选：纯 JWT 无 Redis（无法主动踢出）、Session（不利于水平扩展） |
| D2 | 权限模型 | 标准 RBAC + 菜单/按钮两级权限 + 数据权限（全部/本部门及以下/仅本人） | 企业通用模型；若仅单校单部门可简化为角色+菜单，删数据权限 |
| D3 | 借用人主体 | 系统内用户（含学生/教师类型），借用单关联 user_id | 保证台账可审计；外部访客借用作为二期扩展（需加临时借用人表） |
| D4 | 审批深度 | 借用/入库/报废走两级人工审批（提交→审核→执行），归还单为确认制 | 兼顾风控与效率；如组织简单可将入库/报废合并为单级审批 |
| D5 | 多仓库 | 支持多仓库（库存按器材×仓库拆分） | 企业标准；初期可只启用一个仓库，架构无需返工 |
| D6 | 逾期与赔偿 | 定时任务自动标记逾期，归还时按系统参数计算违约金（可手工调整） | 若无需违约金，仅保留逾期标记与提醒即可 |
| D7 | 库存口径 | `equipment_stock` 只存"在库数量+锁定数量"，借出中数量由明细汇总 | 单一数据源，避免冗余不一致；报表层用聚合查询 |
| D8 | 消息通知 | 二期扩展（站内信/邮件提醒逾期与库存预警） | 一期以页面提示为主，避免首版范围膨胀 |
| D9 | 外键 | 不使用物理外键，逻辑关联 + 索引 + 应用层事务保证 | MySQL 高并发与未来分库分表的常见取舍 |
| D10 | 部署形态 | 一期 jar + nginx 反向代理（可选 Docker Compose） | 由实际部署环境决定 |
